❯ List the wifi7-explorer MCP tools                                             

● The wifi7-explorer MCP server has 12 tools. These descriptions come from the
  server's own tool schemas.

  Model and rules (nothing boots)

  Tool: get_model
  What it does: Shows the explorer's scope: model.json versions, the admitted
    dimensions and their smoke-tested values, pinned hostap/kernel, which
    stages (P0–P4) are implemented, which tests run_hwsim_test accepts, every
    rule and UND.* question, and how dimensions depend on each other.
  ────────────────────────────────────────
  Tool: explain_rule(rule_id)
  What it does: Shows the full entry for a SEC.*, AO.*, UND.* or P0.* ID: what
    kind of rule it is, review status, the check, exceptions, cited sources
    (section, page, strength) and examples.
  ────────────────────────────────────────
  Tool: validate_candidate(candidate)
  What it does: Runs P0 then P1. The status is MALFORMED, SPEC_RULE_VIOLATION,
    SPEC_UNDETERMINED or PASSES_MODELED_RULES. A passing candidate also gets
    the P2 result (SUPPORTED or UNRESOLVED, with its evidence).

  Agent chain (#74, nothing boots)

  Tool: why_pruned(candidate)
  What it does: Gives the planner's role for the candidate (malformed / pruned
    / undetermined / unsupported / not_run / probe / supported). For each
    finding it lists the sources, how ConfigSpace encodes the rule, and the
    runs that test it.
  ────────────────────────────────────────
  Tool: permitted_alternatives(candidate, max_changes=1, limit=10)
  What it does: Finds the smallest rule-passing changes to the candidate,
    using 1–3 admitted dimensions, with SUPPORTED ones ranked first.
  ────────────────────────────────────────
  Tool: minimize_contrast(contrast | run_a+run_b, facts, max_guest_runs=20)
  What it does: Runs Picire to find the fewest changes that reproduce side B's
    facts. This one does boot guests (up to 40 runs). A result is labeled
    PENDING_VERIFICATION until the 3/3 verify step passes.

  Running in simulation (boots fresh UML guests)

  Tool: run_hwsim_test(test, negative_experiment=false)
  What it does: Runs one of hostap's own runnable tests (about 30 s). A test
    that breaks a rule is refused unless you run it as a labeled negative
    experiment.
  ────────────────────────────────────────
  Tool: run_candidate(candidate, negative_experiment=false)
  What it does: Validates the candidate, then runs it through the adapter
    (about 30–60 s) and returns its P3 status and behavior record.

  Campaigns

  Tool: plan_campaign(seed=0, budget=20, build_on_runs=true)
  What it does: Builds a pairwise allpairspy plan of executable candidates
    (nothing boots) and returns a plan_id.
  ────────────────────────────────────────
  Tool: run_campaign(plan_id, campaign_id?, retries=1)
  What it does: Runs each candidate in the plan through the cache or a fresh
    guest and writes campaigns/<id>/. It refuses to run if the simulation
    image is older than the harness files.
  ────────────────────────────────────────
  Tool: list_campaigns()
  What it does: Lists the campaigns with their P3 counts.
  ────────────────────────────────────────
  Tool: get_campaign(campaign_id, candidate_id?)
  What it does: Shows one campaign's pruning funnel, rejected-cases table and
    each candidate's status. With a candidate_id, it also gives that
    candidate's attempts and behavior signatures.

  Runs from run_hwsim_test, run_candidate and minimize_contrast are trials in
  the git-ignored runs/hwsim-logs/. run_campaign writes its output to
  campaigns/<id>/, which only counts as evidence once someone reviews and
  commits it.

  setups: link 0 uses SAE-EXT-KEY and link 1 uses OWE.

  1. SEC.MLD_COMMON_SUITES: the links share no AKM

  - Why it fires: link 0 offers ['SAE-EXT-KEY'] and link 1 offers ['OWE'], so no
    AKM is offered on both. A multi-link association needs at least one AKM in
    common.
  - Source: IEEE 802.11be-2024 §12.6.2 RSNA selection, PDF p. 411 (printed 410),
    shall. The affiliated APs of an AP MLD must have the same RSNE apart from
    the AKM Suite List and MFPR, and must have at least one AKM in common. The
    WFA WPA3 guide §3.1.4.1 (p. 28) repeats this as a NOTE, which is guidance
    only.
  - Experimental validation: cited_runs_only. No committed run breaks this rule;
    its coverage rows cite runs 1793897820 and 1794875139.

  2. SEC.MLD_SAME_RSNXE: the links' RSNXEs differ

  - Why it fires: hostapd sets the SAE hash-to-element bit on link 0 because it
    uses SAE-EXT-KEY. Link 1, with OWE only, advertises no RSNXE at all.
  - Source: the same §12.6.2, PDF p. 411, shall. Every link must advertise the
    same RSNXE, if one is included. The project uses the strict reading Michelle
    chose for #95: once any link includes an RSNXE, every link must advertise
    the same one.
  - hostap code at the pinned commit:
    - src/ap/wpa_auth_ie.c:549-557: rsnxe_capab() sets the bit when a link has
      SAE-EXT-KEY.
    - src/ap/wpa_auth_ie.c:601-611: wpa_write_rsnxe() writes no RSNXE when no
      bit is set.
  - Experimental validation: broken_in_a_run. The labeled negative experiment
    runs/experiments/1794875139 breaks this rule, and the explorer candidate
    still PASSed. So hostap at the pinned commit doesn't enforce this rule
    itself; the explorer prunes the candidate on the spec rule.

  The campaign could never produce this candidate. model_json.apply gives every
  link the same AKM and cipher, so neither rule can fire there; ConfigSpace
  doesn't encode them and P1 checks them instead. That's why campaign_assignment

  The likely fix is to give link 1 SAE-EXT-KEY as well; that matches the
  client's AKM list. permitted_alternatives on this candidate would list the
  nearby versions that pass the rules, with any SUPPORTED ones first.
