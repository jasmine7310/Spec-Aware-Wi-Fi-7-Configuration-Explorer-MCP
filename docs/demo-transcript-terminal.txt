  The rule: SEC.MLD_COMMON_SUITES

  According to explain_rule, this is a normative rule, and its review status is
  "reviewed".

  What it requires. All links of one AP MLD must advertise the same RSNE and
  RSNXE, except for two parts: the AKM list and the MFPR bit. In practice:
  1. Every AP link uses the same pairwise cipher.
  2. The links' AKM lists have at least one AKM in common.

  Why your candidate fails. Link 0 offers only SAE and link 1 offers only
  SAE-EXT-KEY, so the two lists have nothing in common and condition 2 fails.
  The STA supporting both AKMs doesn't help: this rule is about the AP MLD's own
  configuration. The client side is covered by a separate rule,
  SEC.MLD_CLIENT_COMMON_AKM.

  What it doesn't require:
  - The AKM lists don't have to be identical. One shared AKM is enough. An AKM
    offered on only some links can still be used for a non-ML association with
    that link's AP.
  - MFPR may differ per link.

  Cited sources (as recorded in rules.yaml):
  - IEEE 802.11be-2024 §12.6.2 "RSNA selection", PDF p. 411 (printed 410),
    shall. Its two requirements: affiliated APs advertise identical RSNE/RSNXE
    apart from the AKM Suite List and MFPR, and they share at least one AKM.
    Checked in the PDF by Michelle (2026-10-31) and in the PDF text by Claude
    (2026-11-02).
  - WFA WPA3 Deployment Guide §3.1.4.1 "APs", p. 28. This is a NOTE (guidance
    only), so it explains the rule but isn't its authority: AKMs on every link
    can be used for ML associations, the others only for non-ML associations.

  hostap test that matches this case. Your config is the rule's own "disallowed"
  example, which matches hostap's eht_mld_no_common_key_mgmt. That test is
  designed to fail. Its sibling eht_mld_invalid_link covers the WPA-PSK vs. SAE
  version of the same mistake.

  How to fix it

  Give the links a shared AKM. For example, set link 0's akms to ["SAE", 
  "SAE-EXT-KEY"], or use ["SAE-EXT-KEY"] on both links. I haven't validated
  either version; I can run them if you'd like.
